# 后续自动化计划：减少逐模型人工操作

状态：**设计文档，尚未接入主流程**。需求记录先记录，后续再实施。本文中的自动识别、建议入口和验收目标均不是当前已有功能。

## 要解决的问题

现有工具已经复用了转换、绑定、包管理与恢复命令，但处理样本 A和样本 B时，仍由人工或 AI 完成了解压、挑主模型、检查骨骼、写 boneMap、判断衣物规则、选择朝向及初始姿势参数。这只是把操作封装成命令，还没有把判断过程充分产品化。

目标是：常见模型交给工具后，自动完成可可靠推导的步骤，并生成结果和识别依据。只有信息不足、来源互相矛盾，或需要主观审美调整时，才需要覆盖配置。不能让每个新模型都重新经历一次源码修改与多轮试错。

## 已有能力与真正的缺口

| 环节 | 当前已实现 | 后续需要补充 |
| --- | --- | --- |
| 输入 | 导入支持格式的模型文件 | 直接接收 ZIP，安全解压与主模型选择 |
| Assimp 兼容 | Windows Bun 使用 WASM；PMX 四维附加 UV 处理 | 将兼容行为作为稳定测试能力维护，而非逐模型补丁 |
| 人形角色 | VRM 元数据；非 VRM 显式 boneMap | 从通用命名、层级及真实权重自动建立映射 |
| 衣物 | 源材质、混合权重、连通部分、可配置分类规则 | 自动选择规则，识别不确定或混合的部件 |
| 朝向与姿势 | 按 profile 对齐朝向、肩外移、手臂外展 | 根据源骨架与几何提出保守的初始配置 |
| 预览与报告 | 实际输出预览；骨骼归属示意；workflow 报告 | 报告每项自动判断的证据、置信度及待确认项 |
| 包管理 | 可配置路径、导入/导出、多包启停、备份/恢复 | 直接复用，不再建立另一套部署逻辑 |

参考实现：`src/importer.ts`、`src/humanoid.ts`、`src/pack-manager.ts`、`scripts/workflow.ts`。本次真实样本记录见 `pmx-model-tests.md` 与 `windows-client-test.md`。

## 期望的使用方式

后续入口应接受一个模型文件或 ZIP。用户只需提供输入；名称、输出位置、是否绑定人形及初始绑定配置尽量从输入与已有设置推导。具体命令名称后续实现时确定，本阶段不增加占位命令。

默认结果应包含皮肤包、预览、识别报告及可保存的覆盖配置。导入库和部署继续复用现有管理器，目标路径从管理配置读取；不要求每次重新填写。写游戏目录仍应是明确选择，部署前保留现有备份、冲突检查与恢复能力。

原有显式配置入口保留，方便复现、批处理及修正特殊模型。自动化不能降低可解释性，也不能覆盖测试已经确认过的 profile。

## 1. 输入归一化与主模型选择

建立统一输入准备层，返回选中的模型、资源根目录、来源哈希和选择报告，不把解压逻辑散落在各个格式导入器中。

- ZIP 解压拒绝越界路径、盘符、链接、重复目标路径；设置解压条目数、单文件与总展开大小限制。
- 保留原资源目录、中文名称、贴图相对路径和来源说明，不改写原 ZIP。
- 缓存以输入内容哈希区分；重复输入可复用准备结果，不能覆盖其它模型的缓存。
- 候选评分综合格式元数据、人形骨骼完整度、真实蒙皮使用情况、网格规模与主对象关系。文件名中的 weapon/武器只能作为辅助证据，不能作为唯一标准。
- 同一包内有角色、独立武器时，应能明确选角色；存在两个完整角色或多个难以区分的衣装版本时，输出候选列表，要求指定入口，不擅自选最大文件。
- 识别出皮肤包时交给已有包导入器，避免把 mcpack 当成模型重新转换。

## 2. 自动骨骼映射

优先读取源格式明确的人形元数据，其次使用可复用的命名约定适配器；避免为每个角色写一张专用名称表。

候选约定包括 VRM、常见 MMD 日文/中文名称，以及后续单独验证的 Mixamo 等。名字归一化可处理大小写、常见命名空间和分隔符，但最终选择还需要检查父子层级、关节位置和实际顶点权重。

重点规则：

- MMD 的控制骨与承载权重的变形骨要区分，例如左足/左足D。优先检查实际蒙皮权重和变形链，不只取第一个同义名称。
- 不把 IK、物理或控制辅助骨直接当作玩家关节。
- 左右侧、肩到手、髋到脚的链应相互一致。重名、缺链、层级冲突或方向异常需要报告。
- 不因“存在蒙皮”就判定为可用人形；也不在识别失败时悄悄降级成静态 T 姿势并报告成功。
- 绑定所需角色必须完整，才进入自动人形转换；显式 static 仍作为用户可选模式。

每个映射记录源节点、采用的约定、权重与层级证据、被排除的候选及不确定性。通用约定识别失败时才使用模型覆盖配置。

## 3. 自动衣物与附属部件分类

继续使用转换前的数据，而不是在最终 poly_mesh 上凭外观重新猜测。应保留材质/网格身份、源骨骼层级、权重，以及拆分后的来源关系，供分类、预览和问题追踪使用。

判断顺序：源格式的明确语义 → 材质和网格线索 → 连通部分 → 骨骼/物理链 → 权重分布。名称只是线索，不能单靠“衣”或“服”把整件材质归躯干。

- 独立裙摆、披风、飘带等附属链应与腿的直接归属分开处理。裙骨父级在腿下，并不代表裙面应刚性跟腿摆动。
- 同一服装材质可能同时包含上衣、手套、靴子；不能整材质锁到躯干。
- 袖子跨胸、肩、臂的混合权重需要保留，并先在源骨架上计算新的静止姿势，避免冻结后硬挪切片。
- 对展开的三角形，重建连通关系必须考虑位置与权重签名，不能仅凭坐标合并不同衣物层。
- 高置信的独立部件可整体归属；真正连续的躯干与手臂混合区域需要专门处理，不把整件上衣强制归单个骨骼。
- 混合材质、未知附属链、低置信部件应显示在归属图里，并生成局部覆盖项，避免要求用户手填整张配置。

现有 `body`、`arm-components`、`weighted-components` 是可复用的执行能力。后续需要自动选择与验证这些能力，而不是继续增加以角色名字为条件的分支。

## 4. 自动朝向与初始姿势

朝向优先使用明确的源坐标约定，并用左右关节、躯干向上方向和面部/手脚线索交叉检查。不能因为两个 PMX 都需要转 180°，就认为所有输入都应如此。

肩外移、手臂外展应依据归一化后的体型与衣物范围给出保守建议，不能把 Shino 的 0.5/6° 或另外两个角色的 0.3/6° 当作全模型默认答案。

后续可建立小范围参数搜索，评估待机及代表性摆臂时的穿插，同时约束肩宽变化、手臂外展和肩袖接合。只优化“无碰撞”会再次得到肩太宽、手臂张太开的姿势，必须同时约束外观偏差。

报告区分几何抽样、完整碰撞检查与客户端观察。顶点间距为正不等于三角形完全不相交，几个离线动作也不代表全部玩家动画通过。静止姿势可自动改善，但自然与否仍有审美判断空间。

## 5. 配置与报告的职责

将配置分为三层：格式/命名约定的通用规则、根据当前模型生成的识别结果、测试确认的覆盖项。优先级为用户覆盖高于自动结果，自动结果高于保守默认。

自动报告至少包含：

- 输入与外部资源清单/哈希、选中模型及候选选择依据。
- 骨骼约定、完整角色映射、缺失/冲突信息。
- 每个材质和部件的归属、规则来源及低置信区域。
- 朝向、姿势建议与几何检查结果。
- 最终有效配置，以及工具/规则版本，便于复现与比较。
- 转换、文件校验、库导入、部署与客户端验收的独立状态。

生成的配置是可检查的结果，不是用户每次都必须手写的前置条件。相同输入、规则版本与覆盖项应产生相同识别结论；包 UUID 和备份时间等运行元数据可单独变化。

## 实施阶段与验收门槛

| 阶段 | 交付 | 验收标准 |
| --- | --- | --- |
| A：输入自动准备 | 文件/ZIP 统一输入、资源定位、候选选择 | 两个现有 ZIP 不需人工解压或挑主模型；多角色歧义与恶意路径测试通过 |
| B：骨骼约定识别 | VRM/MMD 自动映射及证据报告 | Shino、样本 A、样本 B不需手写 boneMap；控制骨/变形骨、重名与缺链有回归 |
| C：衣物规则推导 | 自动选择部件分类方式和局部覆盖 | 三个角色不需手写材质名表；裙子不误跟单腿、靴子不锁死、袖子问题可定位 |
| D：姿势建议 | 体型约束、穿插检查、保守参数搜索 | 同时改善手臂穿模与外观偏差；无法兼顾时明确报告，而不是不断增大肩宽 |
| E：入口收敛 | 一次输入完成准备、转换、预览和可选管理操作 | 常见输入无需改源码、写 workflow JSON 或维护实验脚本；显式覆盖与旧接口仍可用 |

先完成 A/B，再逐步实现 C/D；E 随各阶段收敛，避免只新增一个包装命令、内部仍要求大量逐模型手工判断。

## 测试与证据

通用规则必须用独立的小型合成模型覆盖：命名约定、控制骨/变形骨、混合袖子、裙骨挂腿、同材质手套/靴子、展开顶点、坐标朝向及歧义候选。不能只把三个现有角色的名称写进规则后就称为自动识别。

三个真实角色用于本地集成回归和效果比较。源 ZIP、模型、贴图、生成皮肤包及管理器备份继续留在忽略目录，不为了测试而提交第三方二进制资产。私有样本缺失时应明确跳过对应集成验证；合成单元测试仍须独立运行。

最终游戏端仍由测试者操作，至少观察显示、穿戴、待机、走路、挥手、持物及转头。原始静态模型与六部分人形目标的差异要保留在报告中。

## 不在本轮计划内的承诺

自动化可以减少识别和配置工作，但不会凭空消除目标格式的限制。当前六部分刚性 poly_mesh 不具备原模型的运行时平滑蒙皮、独立肘膝弯曲、MMD IK 或头发/裙摆物理。

保留额外源骨骼、增加专用动画或引入其它目标表达方式，需要单独验证客户端支持与动画适配，不能把这些效果写成自动识别完成后的既有能力。未知模型也不承诺一键完美；目标是常见情况自动处理、特殊情况给出明确原因和最小覆盖范围。
