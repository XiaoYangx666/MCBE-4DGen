# 第一阶段：现有纹理链路审查与基准

> 分支 `research/texture-allocation-v2`　基准 `main@9ce2923`
> 全部数字由 `scripts/research/atlas/run-stage1.ts` 生成，明细见
> `data/stage1-fixtures.md`、`data/stage1-real.md`、`data/stage1-summary.json`。

## 0. 结论先行

1. **现有分配的真实目标是「世界表面积」，不是「纹理像素密度」。** 材质权重只以
   `(Σ area·w)^0.85` 的形式进入矩形面积，UV 跨度只影响长宽比。因此两个世界面积相同、
   但原生纹素密度相差 25 倍的材质，得到完全相同的图集像素（3 844 px 对 3 844 px）。
2. **桌面端跨材质合并让权重彻底失效。** 共享贴图的两个材质只要 UV 盒相接或重叠，
   就会被 `mergeUvCharts` 合并成一个区域。实测：`shared-texture` 场景对任一材质设置
   0.25×～4× 权重，最终纹理密度都是 **1.00×**（完全无响应）；`same-texture-different-uv`
   同样为 1.00×。
3. **权重响应存在死区。** 网页版某材质在 0.25× 与 1× 下密度完全相同（7 733 对 7 733）；
   桌面端睫毛材质在 0.25×→4×（16 倍）之间密度只从 3 821 变到 4 084（+6.9%）。
4. **矩形内 17%～34% 的像素从未被采样。** 6 个真实模型的「矩形内 UV 占比」为
   66%～83%；网页版只有 53%～70%。128×128 下这不是小数：约 4 000～7 000 像素/模型。
5. **图集已经被填满，但填充的是包围盒而不是有效纹理。** `allocated` 89%～97%，
   而 `UV 覆盖` 只有 47%～65%。继续提高「利用率」必须减少包围盒浪费，而不是塞得更满。
6. **细节材质被系统性饿死。** 真实模型中面部/眼睛的采样比通常比服装/头发低
   16～55 倍（如 `shino` 的 Eye 0.0002 对 Cloth2 0.0111）。这是面积分配的直接后果，
   不是调参问题。
7. **桌面端与网页版不是同一算法的两个适配层，而是两套语义不同的规划器**：
   分组键、是否裁切、gutter 宽度、装箱顺序、共享规则、权重作用位置都不同。
   同一模型上岛数可以相差 3～7 倍（`furina`：网页 81 岛，桌面 12 岛）。

因此：现有实现可以保住的优点是「UV 数学、wrap 采样、确定性装箱、alpha/颜色烘焙」，
但**分配层需要重做**。

## 1. 范围与方法

本阶段只做审查与基准，不改生产代码。为此建立了独立工具链
`scripts/research/atlas/`：

- **中性输入模型**（`types.ts`）：每个材质批次携带世界面积、逐三角面世界面积、
  连续 UV、源纹理（sRGB RGBA）、wrap、alpha 语义。桌面端和网页版都能无损映射到它。
- **两个生产规划器的移植**（`baseline-desktop.ts`、`baseline-web.ts`），
  并用两种方式校验：
  - `tests/webapp-atlas-port.test.ts`：11 个场景的矩形/岛划分与真实 `planAtlas`
    **逐项相等**；
  - `run-stage1.ts`：在 6 个真实模型上直接运行未修改的 `optimizeTextures`，
    对比其 `report.regions` 与本移植版的矩形，**120/120 完全一致**
    （23/23、25/25、27/27、7/7、22/22、12/12）。
- **统一渲染器**（`render.ts`）：footprint 面积过滤 + 双线性，sRGB 输出，
  与生产相同的颜色/alpha 烘焙。这样比较的是**规划器**，不是 libvips 与 canvas 的差异。
- **统一测量**（`metrics.ts`）：覆盖率、精确纹素计数、重心采样误差。
- **真实模型**：6 个 PMX 派生角色（22k～88k 三角面，14～27 个材质），
  记录路径与 SHA-256。素材不入库，报告中明确标注。

## 2. 完整数据流

### 2.1 桌面端（Node / sharp）

```
importModel
  └─ prepare-model：世界变换、坐标归一
      └─ mesh-optimizer（可选减面，保持材质分组）
          └─ optimizeTextures(clone):
               ├─ inspectModel
               ├─ textureCharts(doc)                     ← 分组 + 分岛 + 合并
               │    key = hash(贴图字节) + factor + alpha + wrap
               │    buildUvCharts = splitUvIslands + mergeUvCharts
               ├─ 每岛：连续 UV 包围盒 → 整 tile 数 → 整像素 crop(±1 texel)
               ├─ 每岛：Σ 世界面积（按材质名）→ weightedArea = Σ area·weight[name]
               ├─ compact 分配：demand ∝ weightedArea^0.85；二分全局 scale
               ├─ pack()：best-short-side，crop 岛允许 ±20% 拉伸，无旋转
               ├─ 末尾：非 crop 岛宽高向下取整到 tile 倍数
               ├─ sharp：crop → resize(lanczos3) → 烘焙 factor/alpha
               ├─ gutter：用源 wrap 语义填充 padding=2
               └─ UV 重映射 → 每个区域只保留一个材质对象
          └─ validateModel → bedrock-exporter
```

关键点：**分组发生在分配之前**。共享贴图 + 相同采样参数的材质会进入同一组，
再被 `buildUvCharts` 按 UV 连通性/重叠性合并。合并后的区域只有一个矩形、一个
`weightedArea`，最终所有 primitive 被 `setMaterial(region.material)` 统一成
**该区域第一个材质**。材质身份在这一步被丢弃。

### 2.2 网页端（three.js / canvas）

```
load model (three.js)
  └─ extractModel：遍历可见 Mesh，烘焙 matrixWorld，按 material.uuid 聚合
       └─ SourceBatch{ positions(世界), uvs, area, texture, alpha… }
          └─ 材质筛选（included 集合，按 batch.key）
              └─ reduceBatches（可选减面）
                  └─ 权重：batch.area *= weight
                      └─ convertBatches:
                           ├─ triangleAreas(batch) 归一化到 batch.area
                           ├─ planAtlas：buildUvCharts → demand ∝ area^0.85
                           │    4 种排序 MaxRects，pad=1，二分 scale
                           ├─ renderAtlas：canvas drawImage / 逐像素 wrap 采样
                           ├─ remapUvs
                           ├─ measureAtlasUsage（栅格化最终 UV）
                           └─ buildBedrockGeometry → skin pack
```

关键点：网页版**不裁切、不合并跨材质岛、不做整 tile 对齐**；每个材质批次可以
有多个岛，但岛之间不共享矩形。权重直接缩放 `batch.area`，因此对同一材质的所有岛
等比生效。

### 2.3 分叉对照

| 维度 | 桌面端 | 网页端 |
|---|---|---|
| 分组键 | 贴图内容哈希 + factor + alpha + wrap | `material.uuid`（+ 提取时 texture key） |
| 跨材质合并 | **会**（UV 相接/重叠即合并） | 不会 |
| UV 裁切 | 整像素 crop（±1 texel） | 无，按岛包围盒 |
| padding | 默认 2 | 1 |
| 最小岛尺寸 | crop 岛 3px，非 crop 岛 1 tile | 3px |
| 装箱 | best-short-side，单一顺序，crop 岛可拉伸 | MaxRects，4 种排序取最优 |
| 材质权重 | 规划内按**材质名**加权面积 | 规划前按 batch 缩放面积 |
| 重复材质名 | 权重/统计按名字合并 | 按 uuid 独立 |
| gutter 语义 | 按源 wrap 填充 | 复制边缘（clamp） |
| 覆盖率统计 | 三角面采样 + alpha>0 | `textureCoverage` 统计整张图 alpha>0（含 gutter） |

最后一行值得单独指出：网页版展示的 `textureCoverage` 来自
`coverageOf()`，它统计整张画布的 alpha>0 像素，**包含 gutter 和纯色填充**，
因此会系统性高估真实采样率。桌面端的 `sampledUtilization` 才是三角面覆盖率。

### 3.3 合成场景（节选）

完整表见 `data/stage1-fixtures.md`。

| 场景 | 现象 | 数据 |
|---|---|---|
| `shared-texture` | 桌面端把两个材质合并成 1 个岛 | Body/Face 各得 7 688 texels，密度 1 922 vs 30 752（16×），权重扫描 1.00× |
| `same-texture-different-uv` | 同面积、UV 跨度 0.2 vs 1.0 | 两材质各 3 844 px；原生纹素需求相差 25 倍 |
| `sparse-island` | UV 盒覆盖满，三角面只占 3.8% | 矩形 15 376 px，UV 覆盖 602 px，浪费 96% |
| `tiny-islands` | 40 个亚像素岛 | 桌面端 content 55.4%，UV 覆盖 **0.4%**，rect 浪费 9 006/9 073 px |
| `overlapping-uv` | 两材质 UV 完全相同、贴图不同 | 正确保持为 2 个矩形，未错误共享 |
| `character` | 面部 0.057 m²，头发 2.4 m² | Face 采样比 0.001，Hair 0.028 |

`tiny-islands` 的根因是桌面端 crop 的 `±1 texel` 量化：UV 跨度只有 0.256 个源纹素，
crop 仍保留 2 个纹素，随后按世界面积把矩形放大到 18×18，几何只用到其中 2～3 px。
这不是「装箱不好」，而是**需求单位错了**：按面积分配，却按裁剪窗口映射。

## 4. 七个核心问题的回答

### 4.1 哪些纹理像素实际被最终模型使用？

`atlasTexels` 与 `uvPixels` 给出了精确答案（见 `data/*.md` 的逐材质表）。
在真实模型上，三角面实际覆盖的像素只占图集 47%～65%；矩形内部还有 17%～34%
从未被采样。剩余部分是 gutter、装箱空隙和包围盒内空白。

### 4.2 哪些空间只是被 UV 包围矩形占用？

- 矩形内空白：真实模型 17%～34%；`sparse-island` 96%；`tiny-islands` 99.6%。
- gutter：桌面 pad=2，每个岛固定增加 `2·(w+h)+4` 像素；网页 pad=1。
- 装箱空隙：`emptyPixels`，桌面 3.4%～10.8%，网页 9.1%～15.6%。

必须区分：**矩形内空白不等于可复用**。它可能被线性过滤读到（需要 gutter），
也可能包含三角形之间的缝隙（采样安全但视觉上不可见）。只有同时满足
「无三角形覆盖 + 过滤半径内无三角形 + 不与相邻岛冲突」的像素才能安全复用。

### 4.3 哪些区域因跨材质共享而无法独立调节？

桌面端 `shared-texture`、`same-texture-different-uv` 均被合并为单区域，权重扫描
恒为 1.00×。真实模型中 `nana` 15 个材质只剩 7 个岛、`furina` 27 个材质只剩 12 个岛，
说明合并是常态而非边缘情况。网页版不合并，但同材质多岛共享一个 `batch.area`，
也无法按「部件」调节。

### 4.4 权重变化如何影响真实像素密度？

实测（`data/*.md` 权重扫描表）：

| 场景/材质 | 平台 | 0.25× | 1× | 4× |
|---|---|---|---|---|
| shared-texture / Body | desktop | 1.00× | 1.00× | 1.00× |
| shared-texture / Face | desktop | 1.00× | 1.00× | 1.00× |
| same-texture / DenseUV | desktop | 1.00× | 1.00× | 1.00× |
| few-large-many / Hero | web | 0.69× | 1.00× | 1.26× |
| character / Face | web | 0.35× | 1.00× | 3.33× |
| shino / Emotion2 | web | 0.25× | **1.00×** | 1.98× |
| shino / Eyelash | desktop | 0.98× | 1.00× | 1.04× |

三种失效模式：
1. **合并导致完全失效**（1.00×）；
2. **量化死区**（0.25× 与 1× 结果相同，因最小岛 3px / 整数装箱）；
3. **全局缩放抵消**：`demand ∝ w^0.85`，但图集始终被填满，提高一个材质会压缩其余所有
   材质，大材质自身只得到 1.26×（要求 4×）。

### 4.5 分岛、合并、装箱是否存在不合理的启发式？

- `mergeUvCharts` 的 `overlapsUv` 条件（`joinedArea ≤ unionArea*1.02`）会把**不同材质**
  的相邻 UV 盒合并（`shared-texture` 正是 0..0.5 与 0.5..1 的完美拼接）；
- `sharesMaterial` 用**材质名**判断，重名材质会被视为同一材质；
- 桌面端 crop 的 ±1 texel 对小于 1 texel 的岛过度分配；
- 桌面端末尾的 tile 向下取整会在矩形右侧/底部留下未使用条带；
- 网页端 3px 最小尺寸 + pad=1 在岛数多时产生大量 5×5 有效 9px 的小块；
- 两个平台的装箱都不旋转（正确，保持 UV 方向），但都不考虑岛内实际覆盖形状。

### 4.6 是否有重复采样、重复存储或不必要的图集区域？

- **重复存储**：同一源图被多个不合并的岛分别裁剪、缩放、写入图集。桌面端有解码缓存，
  但没有像素级去重；`overlapping-uv` 场景两个材质必须各存一份（贴图不同，正确），
  而 `shared-texture` 合并后只存一份（正确），区别只由启发式决定。
- **重复采样**：UV 完全重合且贴图相同的两个材质会写到同一批像素（`character` 的
  EyeL/EyeR 各占 15 px 但重叠 16 px），统计上被计两次。
- **不必要区域**：见 4.2；最大来源是包围盒与亚像素量化。

### 4.7 材质、Mesh、Primitive、UV 岛之间哪些关联在处理中丢失？

| 关联 | 现状 | 后果 |
|---|---|---|
| 材质身份 | 桌面端合并后只保留「第一个材质」对象；统计/权重按名字 | 重名材质共享权重，合并后无法区分 |
| Mesh/Primitive | 网页端按 `material.uuid` 聚合成 batch；桌面端按贴图+参数分组 | 同材质的不同部件无法单独删除/加权 |
| 三角形 → 部件 | 网页端有 `PART_CODE`，但只用于骨骼绑定 | 纹理分配无法按部件控制 |
| UV 岛 → 材质 | 岛只记录材质名集合，不记录逐三角形归属 | 共享岛无法拆分预算 |
| 矩形 → 实际覆盖 | 只保留 32² 栅格的 `coverageArea` 估计 | 无法判断可复用空白 |

## 5. 假设状态

| 假设 | 状态 | 证据 |
|---|---|---|
| 权重可以线性控制清晰度 | **证伪** | 4× 只得到 1.04×～3.3×，合并时 1.00× |
| 表面积近似纹理需求 | **证伪** | 同面积、UV 跨度 25× 差异得到相同像素 |
| 跨材质共享只在 UV 重合时发生 | **证伪** | 相邻拼接（union≈bbox）也会合并 |
| 图集已经接近饱和，提升空间有限 | **证伪** | 矩形内 17%～34% 从未采样 |
| 提高 allocated utilization 就能提升质量 | **未证实（倾向否定）** | 网页版 allocated 更高但 UV 覆盖更低、误差更大 |
| 小岛主要输在装箱 | **证伪** | `tiny-islands` 是 crop 量化问题，装箱只占次要部分 |
| 两平台结果数值等价 | **证伪** | 岛数差 3～7 倍，矩形完全不同 |
| 128² 下 UV 覆盖率与视觉质量正相关 | **未决** | 需要第三阶段的同视角/采样误差实验 |

## 6. 限制

- 真实模型均为动漫角色（PMX 派生），没有写实 PBR 或硬表面样本；
  结论对「少量大材质 + 大量小材质」的角色类模型最可靠。
- 采样误差以源纹理双线性采样为参考，衡量的是**细节保留**，不衡量 UV 拉伸
  （拉伸会同时改变源与图集的采样点，误差仍可能低）。第三阶段会补充
  「每三角面纹素密度分布」与局部清晰度统计。
- 桌面端生产误差使用 libvips lanczos3，研究渲染器使用面积过滤；
  两者只在各自内部可比，跨渲染器比较不作结论。
- `maxRSS` 是进程级峰值，不能精确拆分到单个阶段。

## 7. 对第二阶段的输入

1. 预算单位必须是**纹理密度**（texels / 世界面积），且要能表达「相对优先级」，
   而不是把权重塞进面积幂函数。
2. 共享必须是**显式、可撤销**的决策，并且不能把不同材质的预算合并。
3. 需要区分四种空白：gutter、包围盒空白、岛内孔洞、装箱空隙；只有后两类可能复用。
4. 需要保留部件级（primitive/mesh）归属，才能在删除部件时回收其独占需求。
5. 128×128 是硬约束，因此「提高某材质」必然意味着「其他材质让出」；
   控制模型必须明确这一点，而不是假装可以同时提高所有材质。
