# 第二阶段：分配模型研究与候选设计

> 分支 `research/texture-allocation-v2`
> 原型：`scripts/research/atlas/core/budget.ts`（8 个单元测试）
> 本阶段只做模型与可测试原型，不做 UI，不改生产代码。

## 1. 现有分配到底在优化什么

桌面端与网页端共用同一条需求公式（`texture-optimizer.ts`、`atlas.ts`）：

```
demand_i = (Σ_triangles area · weight_material)^0.85
chart_w ∝ sqrt(demand_i · aspect_i) ,  chart_h ∝ sqrt(demand_i / aspect_i)
```

然后二分一个全局 `scale`，使所有（含 gutter 的）矩形刚好塞进 128×128。

这个公式有三个隐含假设，全部与实测不符：

1. **假设「世界面积 ∝ 纹理需求」**。但纹理需求是「源纹素」：
   同一世界面积、UV 跨度相差 25 倍的两个材质，源纹素差 25 倍（第一阶段实测）。
   公式给它们相同的图集像素。
2. **假设 `0.85` 次幂是「保护小材质」**。它实际做的是压缩大材质的需求，
   使权重与结果之间变成 `density ∝ w^0.85` 再被全局 scale 二次调制；
   在合并区域里则完全失效（实测 1.00×）。
3. **假设矩形面积可以直接当作质量单位**。矩形里只有 66%～83% 被采样
   （真实模型），因此「分配了 100 px」不等于「得到 100 px 的清晰度」。

## 2. 权重应当控制什么

固定 128×128 预算下，任何「提高某材质」都必须让其他材质让出空间。
因此权重只能是**相对量**。有两个自洽、可解释的选择：

### 2.1 A. 世界纹理密度（texel density）

```
目标：d_m = d̄ · w_m        [atlas texels / m²]
⇒ 目标面积 A_m = d_m² · S_m = d̄² · w_m² · S_m
```

- 权重 2× ⇒ 每平方厘米的纹理像素 2×（线性、可预测）。
- 图集容量决定 `d̄`：`d̄ = sqrt(可用像素 / Σ w_m² S_m)`。
- 大材质天然占更多像素，因为它有更多平方厘米需要覆盖。
- 缺点：小材质（眼睛 0.006 m²）只得到 30～40 px；128² 下这是不可避免的。

### 2.2 B. 原生细节保留率（retention）

```
目标：r_m = r̄ · w_m        [atlas texels / native texels]
⇒ 目标面积 A_m = r_m · T_m = r̄ · w_m · T_m
其中 T_m = Σ|UV 三角形面积| · srcW · srcH   （该材质真正采样的源纹素数）
```

- 权重 2× ⇒ 保留的源细节比例 2×。
- 默认（权重全 1）让所有材质**损失相同比例的细节**，
  于是「作者在 UV 上投入更多纹素的部位」自动获得更多图集像素。
  这**不是**语义识别：算法不知道那是脸，只知道它有多少源纹素。
- 缺点：如果某个材质用了超大贴图但只覆盖很小的物体，它会被高估；
  用户可以下调权重。

### 2.3 选择哪一个？

两者都能给出线性、可解释的控制，但默认分布不同。第一阶段的证据是：
真实模型上面部/眼睛的原生密度比服装高 3～20 倍，而现有算法把它们压到
更低的保留率。因此**假设** retention 默认更接近作者意图、视觉更好；
这必须由第三阶段的同条件采样误差与局部清晰度实验裁决，不能先验认定。

原型同时实现两种目标，并在测试中验证：

- `density`：等世界面积、权重 2:1 ⇒ 面积 4:1（密度 2:1）；
- `retention`：等源纹素、权重 2:1 ⇒ 面积 2:1（保留率 2:1）；
- 固定预算下，单个材质权重 2× 的**绝对**面积只增长约 1.6×（两个材质时），
  这是正确的：它抢走的是别人的份额。UI 必须这样解释，而不是承诺「2× 像素」。

## 3. 技术下限（floor）不是权重

128×128 下，`3×3` 是仍可采样的最小岛。第一阶段发现：小材质经常已经贴在下限上
（例如 `Emotion2` 在 0.25× 与 1× 下密度完全相同）。这不是公式失效，而是
**物理下限**。因此新模型必须：

1. 显式报告 `floorBoundCharts` 与 `floorPixels`；
2. 在 UI 上把「已到最小尺寸，提高权重无效」如实告诉用户；
3. 允许全局提高图集尺寸或减少材质数量作为真正的解决办法。

原型 `solveBudget()` 返回这两个字段，测试覆盖「30 个小材质全部 floor-bound」。

## 4. 独立控制与共享的边界

### 4.1 为什么必须先预算再共享

现有流程是「先按贴图+参数分组 → 合并岛 → 再算一个混合需求」。
一旦合并，两个材质的预算就变成一个数，权重只能整体缩放，无法独立。

正确顺序：

```
几何分析 → UV 岛分析 → 每材质/每岛需求 → 独立预算 → 可选共享 → 装箱 → 烘焙与重映射
```

共享发生在预算之后，只是**装箱层面的复用**，不改变任何材质的预算。

### 4.2 哪些共享是安全的

| 共享形式 | 是否安全 | 条件 |
|---|---|---|
| 完全相同 UV 盒 + 相同贴图 + 相同采样参数 | **安全** | 两个材质读写同一批源像素，图集矩形完全重合，省掉一个矩形与一道 gutter |
| 同一材质的不同岛合并到同一矩形 | 有条件 | 只在合并后覆盖保留率 ≥ 90%、包围盒增长 ≤ 5% 时；否则浪费 |
| 不同材质、UV 不重叠但可拼成更紧的盒 | **不安全（默认禁止）** | 会把两套预算绑在一起，且各自的密度不再可控 |
| 不同材质、UV 完全重叠但贴图不同 | **禁止** | 必然串色 |

原型 Candidate B 只实现第一行（`sharing: 'safe'`），其余保持独立。

### 4.3 分岛/合并策略

- 只在**已有 UV 缝**处分岛（沿用 `splitUvIslands`，已被生产验证）。
- 不在连续岛内部人为切缝：切缝会让相邻三角形映射到图集的不同位置，
  颜色仍正确（同一源图），但密度不连续，可能产生可见接缝。
  第三阶段会把「稀疏岛网格切分」作为独立实验，并专门测量边缘误差。
- 合并只在同一材质内部，且使用更严格的阈值（见上表）。

## 5. 如何减少无用区域

第一阶段把「空白」分成四类，处理方式完全不同：

| 类型 | 例子 | 能否复用 | 处理 |
|---|---|---|---|
| gutter | 每个岛四周 pad | 不能 | 必须保留；成本 = `2(w+h)+4` |
| 包围盒空白 | 斜向肩带 UV 占满 0..1，实际 4% | **不能直接复用** | 只能通过重新映射/切分缩小矩形 |
| 岛内孔洞 | 三角形之间的小缝 | 通常不能 | 过滤半径内可能有三角形，复用会串色 |
| 装箱空隙 | 矩形之间放不下大块的缝 | 可以 | 更好的装箱顺序、允许长宽微调 |

因此「减少无用区域」有两条独立路径：

1. **装箱路径**：减少 `emptyPixels`（矩形之间），不改变任何材质的密度。
2. **需求路径**：不要为「不会被采样的源纹素」付矩形面积。
   这会让稀疏材质的分辨率下降（它本来就被过分配），把面积让给其他材质。

Candidate C 实现第 2 条：`coverageAware` 开关，需求用
`Σ|UV 三角形面积| · srcW · srcH` 而不是 `包围盒面积 · srcW · srcH`。
这是一个明确的**权衡**，不是免费收益，必须在实验里如实呈现。

### 5.1 为什么不做自动隐藏面删除

被删除的几何如果仍被 UV 引用，它的纹素需求就不该继续占据预算；
但「哪些几何被删除」必须是用户的显式决定。算法只做：
`保留三角面集合 → 重新计算 T_m 与 S_m → 重新预算`。
不做不可靠的遮挡剔除。

## 6. 候选方案

| 方案 | 预算 | 共享 | 稀疏处理 | 目的 |
|---|---|---|---|---|
| Baseline-Web | `(area·w)^0.85`，早期合并 | 无（按 uuid） | 无 | 生产网页版 |
| Baseline-Desktop | 同上，跨材质合并 | UV 重叠即合并 | crop ±1 texel | 生产桌面端 |
| **A** | 独立预算（density 或 retention） | 无 | 包围盒需求 | 验证「独立 + 线性」 |
| **B** | 同 A | 仅安全共享（UV 盒完全相同） | 包围盒需求 | 验证「共享是否值得」 |
| **C** | 同 A | 无 | coverage-aware 需求 | 验证「稀疏岛是否该按实际采样计费」 |

A/B/C 共用：源感知长宽比、不裁切、连续 UV 映射、同一 MaxRects 装箱、
同一渲染器与测量。唯一变量是预算单位/共享/稀疏策略。

### 6.1 为什么去掉 crop

桌面端的 crop 是为了「只把用到的源像素搬进图集」。但候选方案直接按连续 UV
包围盒逐像素采样源图（与网页版一致），效果等价，且：

- 没有 ±1 纹素量化（`tiny-islands` 的 99.6% 浪费消失）；
- 没有整 tile 向下取整留下的条带；
- repeat/mirror 的跨缝 UV 不需要物化多个 tile。

代价：每个目标像素要算一次源采样（128² 最多 16k 次），可忽略。

### 6.2 长宽比必须源感知

```
aspect = (spanU · srcW) / (spanV · srcH)
```

只用 UV 跨度会把 1024×256 的贴图区域压成正方形，造成 4× 各向异性失真。
两个生产实现都做了源感知（桌面端用初始矩形宽高，网页版用 `aspectOf`），
候选方案保留这一点，并把「各向异性」作为诊断输出。

## 7. 预期与需要验证的假设

| 假设 | 验证方式 |
|---|---|
| retention 默认比 density 视觉更好 | 6 个真实模型的采样误差、面部/头发局部清晰度 |
| 权重在独立预算下线性可控 | 0.25/0.5/1/2/4 扫描，检查目标材质相对密度 |
| 安全共享能省像素且不降低任何材质密度 | B vs A：UV 完全重合的材质（眼睛、成对饰品） |
| coverage-aware 能提高全局密度 | C vs A：全局密度、稀疏材质自身密度、误差 |
| 先预算后共享优于先共享 | A/B vs Baseline 的权重扫描响应 |
| 去掉 crop 不降低质量 | 候选 vs Desktop 的 tiny/sparse 场景误差 |
| 128² 下 floors 是主要瓶颈 | floorBoundCharts 统计与权重死区 |
